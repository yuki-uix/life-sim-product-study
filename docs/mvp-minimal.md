# 当前 MVP：三回合的生活取舍

状态：依据产品复审修订的范围提案，尚未实现、未冻结。日期：2026-10-26。

用户希望继续保持小范围；实际反馈是有经营感，但多局“仿佛存在人生最优解”。因此本轮调整验证目标，不恢复此前 20 项事件与完整模拟。依据见 [独立产品分析](lead-product-analysis.md)。

## 第一层验证什么

**有限时间和资金下，玩家能否围绕自己在意的事作出取舍，并实际感受到得到与放弃。**

此前“18 岁选教育、30 岁选职业”的固定分支不再是当前方案。先验证一个青年期生活片段，不承诺从出生到死亡的完整模拟，也不要求所有玩家追求职业升级。

## 最小范围

| 项目 | 这一层只做什么 |
| --- | --- |
| 内容 | 一个固定人物背景、一个可选择投入的个人项目 |
| 进程 | 3 个短回合，每回合选择一个时间安排；不按年推进 |
| 约束 | 可支配资金与有限时间；时间可用固定行动位表示，不扩成四个状态条 |
| 行动 | 接额外工作 / 投入个人项目，两类行动重复使用 |
| 结果 | 实际资金变化、个人项目的具体产物、错过或保留的机会 |
| 表现 | 简体中文，一个页面复用回合与回顾；无人生总分、成功等级与统一排名 |
| 存档 | 当前一局、实际处境与选择、结构化事件记录及版本 |

个人项目是可选追求，不是胜利条件。两类行动不是道德上的好坏选项；当前处境下某个行动更划算可以成立。

## 回合怎样玩

```mermaid
flowchart LR
    A[查看资金、可用时间和已知机会] --> B[选本回合的时间安排]
    B --> C[结算实际获得与机会成本]
    C --> D{是否还有下一回合}
    D -->|有| A
    D -->|没有| E[并列回顾得到与放弃]
```

| 行动 | 可见收益 | 必须发生的代价 |
| --- | --- | --- |
| 接额外工作 | 增加可用资金 | 占用本回合的时间，个人项目不能同时推进 |
| 投入个人项目 | 推进并可能完成一份可展示的小作品 | 放弃同期额外收入；必要的投入会消耗资金 |

先只做一个具体项目内容，例如一份小作品，并展示阶段产物或完成内容；不能只有一个进度数值或空泛的“你很充实”。项目类型是样本内容，不建设作品编辑器或 AI 实时生成服务。

同一个项目包含一个提前告知的机会窗口，例如完成后可参与一次展示。错过窗口后仍可独自完成，但不会补写成参加过展示。用有限窗口检验“先赚钱、最后补齐一切”是否总能占全好处；这不是为了惩罚赚钱。

当前不设置没有实际用途的“留出机动时间”按钮。未来出现明确的临时机会和时间冲突，再增加这种行动。

## 先做两个体验样本

两份样本共享人物、项目与行动，只调整初始资金、时间承诺或机会窗口，形成不同处境。先用纸面或可点击草稿验证，不直接锁定数值。

- 主要行动尽量保持可选，不能仅靠锁住按钮来证明有深度。
- 回合开始前说明可预见的成本与期限；首轮固定外部变化，不先加随机事件池。
- 用不同偏好检查结果：积累缓冲、完成作品或保留某种安排都可以有理由，不强制开局选价值标签。
- 不保证每个行动在每个局面一样好；检查的是是否存在一条跨不同追求仍几乎全面占优的路径，以及是否有未兑现的代价。

随机性以后可以改变处境与机会；不会用随机抽坏结局来替代真实取舍。

## 第一层验收

1. 每条可行路径能走完 3 回合，结算不产生非法资金状态，始终有可继续的方案。
2. 投入项目能看到具体成果；选择额外工作则确实取得资金、放弃同一时段投入。
3. 已关闭的机会不被结局补发；允许未完成、独自完成和抓住机会等不同事实并列呈现，不给人生评级。
4. 测试者能解释自己为何这样安排、放弃了什么，以及后续结果怎样影响下一回合。
5. 刷新可恢复，不重复结算；回顾的每件事均有实际事件记录。

如果两个样本仍让人觉得“总是同一个按钮最好”，先修正代价与结果，再扩事件数量。不把不同玩家一定选择不同按钮当作验收硬指标。

## 扩展边界

现在只保存回合、当时处境、可用行动、实际投入/结果、项目事实、机会窗口状态、来源事件与存档版本。事件记录仍为未来 sharing 提供事实基础。

后续每次单独评估一项：更多处境、一次外部转折、把这个片段接到其他人生阶段、事件挑选与分享。共同在场可单独做概念验证，不等同于现在建设实时多人服务。

国家统计、健康、关系、完整职业市场、真实死亡、多语言、历史列表、分享模板库继续后置。通用规则引擎、跨年延期队列和完整事件溯源也不属于当前任务。

[较完整 MVP](mvp.md)、[核心玩法 v0.1](gameplay-v0.1.md) 与 [20 项事件目录](event-catalog-v0.1.md) 仍是后续候选，不叠加进入这一层。字段参考见 [事件记录设计](event-records.md)，按实际玩法启用。
